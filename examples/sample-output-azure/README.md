## Why there are several files, and several directories

Artifacts are grouped in a directory per cloud, and within it split one file per
subscription -- and for HCL one per region when that cloud's Terraform provider is
region-scoped. This is a correctness requirement, not tidiness: a shell script
invokes one vendor CLI using your shell's ambient credentials, and a Terraform
provider configuration covers one credential scope. A file that mixed them would
not merely be untidy; for HCL it could import a same-named resource from the wrong
subscription. Large scopes are additionally split into numbered parts for
reviewability.

**Each file must be run with credentials for the subscription named in its
filename.** The cloud and the subscription are both in every filename, so a file
stays self-describing after it is copied out of its directory. See
`manifest.json` for the full index.

### SQL Database is not encrypted with transparent data encryption

- **Policy ID:** `f3c5d6e7-d8f0-48fd-97ab-16585ff981f3`
- **Safety tier:** safest
- **Remediations in this run:** 2
- **API:** `sql.TransparentDataEncryptionsOperations.begin_create_or_update`
- **IaC resource:** `azurerm_mssql_database` (provider >= 5.0)


Enable transparent data encryption so the database files and backups are encrypted.


**Safety**

- Reversible: az sql db tde set --ids <resource-id> --status Disabled

**Caveats**

- Encryption runs as a background scan over the database files. Queries continue during it, but expect additional I/O until it completes -- on a large database that is hours, and 'tde show' reports the progress.
- TDE cannot be disabled again on anything but a Data Warehouse SKU: the azurerm provider rejects the plan, and the reverse command is accepted only for DW databases. Treat this as effectively one-way for a normal database.
- This enables service-managed keys. A policy requiring a customer-managed key for TDE is a separate finding and is not remediated by this.

[Documentation](https://learn.microsoft.com/en-us/rest/api/sql/transparent-data-encryptions/create-or-update)


### SQL Server Microsoft Defender is not enabled

- **Policy ID:** `675d3b4d-8168-4bc8-bae2-ebad12102b53`
- **Safety tier:** safest
- **Remediations in this run:** 1
- **API:** `sql.ServerAdvancedThreatProtectionSettingsOperations.begin_create_or_update`
- **IaC resource:** none; this policy is CLI only


Enable Microsoft Defender for SQL so the server is monitored for anomalous activity and SQL injection.


**Read before applying**

- THIS ADDS A RECURRING CHARGE. Microsoft Defender for SQL is billed per server per month at the subscription's Defender for Cloud rate, and enabling it at the server level is not free the way most remediations in this tool are. Confirm the spend is approved before running this across a fleet -- a default run emits it under a SAFEST banner, because the safety tier measures disruption rather than cost.

**Safety**

- Reversible: az sql server advanced-threat-protection-setting update --ids <resource-id> --state Disabled
- Small incremental cost from the cloud provider.

**Caveats**

- Nothing is interrupted and no connection is affected. Defender inspects telemetry out of band, so the only consequence at apply time is the charge and the alerts that follow.
- Alerts are delivered through Microsoft Defender for Cloud, and email recipients are configured separately. Enabling this without configuring notifications produces findings nobody is paged for.
- This enables Defender at the server level, which covers every database on the server. A vulnerability-assessment storage account is a separate setting and is not configured by this.
- No HCL is generated. The azurerm provider models this through the older securityAlertPolicies API rather than the advancedThreatProtectionSettings endpoint this command calls, and its import id is not the finding's resource id, so no import block can be generated from a finding alone.

[Documentation](https://learn.microsoft.com/en-us/rest/api/sql/server-advanced-threat-protection-settings/create-or-update)


### SQL Server TLS version does not meet minimum requirements

- **Policy ID:** `17af7bf3-0f70-4822-bc09-e41bfd97dbdf`
- **Safety tier:** safest
- **Remediations in this run:** 1
- **API:** `sql.ServersOperations.begin_update`
- **IaC resource:** none; this policy is CLI only


Raise the server's minimum TLS version to 1.2 so older clients cannot negotiate down.


**Read before applying**

- ANY CLIENT THAT CANNOT NEGOTIATE TLS 1.2 STOPS CONNECTING IMMEDIATELY, with a connection-level error rather than a login failure. Check for legacy ODBC and JDBC drivers, .NET Framework applications older than 4.7 that have not enabled TLS 1.2 explicitly, and embedded or appliance clients, before applying. The server does not warn and there is no grace period.

**Safety**

- Reversible: az sql server update --ids <resource-id> --minimal-tls-version 1.0

**Caveats**

- Existing connections are not dropped. The change applies to new connections, so an application with a warm pool can keep working for hours and then fail on its next reconnect -- which is well after the change looks successful.
- This is set on the server and applies to every database on it, including ones with no finding of their own.
- The reversal restores 1.0, which re-opens the finding. Azure also accepts 'None' for no minimum, which this tool never writes.
- No HCL is generated for this recipe. The azurerm provider requires an administrator login and password on azurerm_mssql_server through rules the machine-readable schema does not express, so a generated block would either fail to validate or carry a credential-shaped placeholder. Set minimum_tls_version in whatever module already manages the server.

[Documentation](https://learn.microsoft.com/en-us/rest/api/sql/servers/update)

### Storage Account insecure communication

- **Policy ID:** `0662810d-c71d-46a3-a937-e1c2b24792e4`
- **Safety tier:** safest
- **Remediations in this run:** 2
- **API:** `storage.StorageAccountsOperations.update`
- **IaC resource:** `azurerm_storage_account` (provider >= 5.0)


Require TLS 1.2 or later so clients cannot negotiate a deprecated cipher suite.


**Read before applying**

- A client whose TLS stack cannot negotiate 1.2 will fail. In practice that means very old SDK versions and .NET Framework applications with TLS 1.2 not explicitly enabled.

**Safety**

- Reversible: az storage account update --ids <resource-id> --min-tls-version TLS1_0

**Caveats**

- The reverse command sets TLS1_0, which restores the weakest setting rather than whatever the account had before. If it was TLS1_1, pass that instead.
- Reversing via the HCL is not possible: `az` accepts TLS1_0 and TLS1_1, but azurerm 5.x validates min_tls_version against TLS1_2 alone, so reverting the generated attribute fails at plan time. Use the reverse command above.

[Documentation](https://learn.microsoft.com/en-us/rest/api/storagerp/storage-accounts/update)
