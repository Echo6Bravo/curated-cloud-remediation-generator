## Why there are several files, and several directories

Artifacts are grouped in a directory per cloud, and within it split one file per
account -- and for HCL one per region when that cloud's Terraform provider is
region-scoped. This is a correctness requirement, not tidiness: a shell script
invokes one vendor CLI using your shell's ambient credentials, and a Terraform
provider configuration covers one credential scope. A file that mixed them would
not merely be untidy; for HCL it could import a same-named resource from the wrong
account. Large scopes are additionally split into numbered parts for
reviewability.

**Each file must be run with credentials for the account named in its
filename.** The cloud and the account are both in every filename, so a file
stays self-describing after it is copied out of its directory. See
`manifest.json` for the full index.

### KMS Key automatic key rotation is not enabled

- **Policy ID:** `995e8d78-940a-45bf-bac1-61a1fdb00d7a`
- **Safety tier:** caution
- **Remediations in this run:** 2
- **API:** `kms.EnableKeyRotation`
- **IaC resource:** `aws_kms_key` (provider >= 5.0)


Enable annual automatic rotation of the KMS key's backing material.


**Safety**

- NOT REVERSIBLE: this change cannot be fully undone.
- Small incremental AWS cost.

**Prerequisites**

- Applies only to symmetric encryption keys with AWS-generated material (KeyManager=CUSTOMER, Origin=AWS_KMS).

**Caveats**

- Not supported for asymmetric keys, HMAC keys, keys with imported material, or keys in a custom key store. The call fails on those, so filter findings first.
- 'aws kms disable-key-rotation' stops future rotations but does not undo a rotation that already happened.
- Old key material is retained so existing ciphertext stays readable. Rotation does not re-encrypt existing data.
- Each additional backing key incurs a small monthly KMS charge.

[Documentation](https://docs.aws.amazon.com/kms/latest/APIReference/API_EnableKeyRotation.html)

### S3 Bucket versioning is not enabled

- **Policy ID:** `284b1210-a31e-48ce-97af-f4d825ef132d`
- **Safety tier:** caution
- **Remediations in this run:** 4
- **API:** `s3.PutBucketVersioning`
- **IaC resource:** `aws_s3_bucket_versioning` (provider >= 5.0)


Enable versioning so overwritten and deleted objects remain recoverable.


**Safety**

- NOT REVERSIBLE: this change cannot be fully undone.
- COST SCALES WITH USAGE: charges grow with data volume and have no ceiling. Estimate volume before applying fleet-wide.

**Caveats**

- Versioning can never be fully disabled once enabled -- only suspended (Status=Suspended). Existing object versions remain.
- Storage cost grows because every overwrite retains the previous version. Pair this with a lifecycle rule expiring non-current versions, or cost will climb indefinitely on a write-heavy bucket.
- A bucket with MFA Delete enabled cannot have its versioning state changed with ordinary credentials.

[Documentation](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutBucketVersioning.html)

### S3 Bucket block public access is not enabled

- **Policy ID:** `80b8e9b6-c285-4939-b115-452dfd65bbcc`
- **Safety tier:** safest
- **Remediations in this run:** 2
- **API:** `s3.PutPublicAccessBlock`
- **IaC resource:** `aws_s3_bucket_public_access_block` (provider >= 5.0)


Enable all four Block Public Access settings so the bucket cannot be made public.


**Read before applying**

- CONFIRM THIS BUCKET IS NOT MEANT TO BE PUBLIC BEFORE APPLYING. If it serves a static website, a published dataset or any anonymously read content, that access stops immediately. This tool cannot tell intentional public access from accidental: a Tenable Cloud Security exception does not travel in a findings export, so scope your export rather than relying on the tool.

**Safety**

- Reversible: aws s3api delete-public-access-block --bucket <bucket> --region <region>

**Caveats**

- IgnorePublicAcls and RestrictPublicBuckets act on access that already exists -- existing public ACLs stop being honoured and existing public bucket policies are restricted to this account's principals. The other two flags only reject future attempts to grant public access.
- Account-level Block Public Access combines with this bucket-level setting, and S3 applies the more restrictive of the two. A bucket can therefore already be blocked in practice while still failing this policy, and this command is still the fix for the bucket-level gap.
- Cross-account access granted by bucket policy to specific external principals is also restricted by RestrictPublicBuckets, including non-public delegation. Check for partner or vendor access paths that are scoped by account rather than by a public wildcard.

[Documentation](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutPublicAccessBlock.html)
